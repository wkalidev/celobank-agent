## Changelog

- July 24 2026: **CeloBankAgent's first verification attempt used the wrong solc version — corrected and locally byte-verified.** `artifacts/build-info/` is gitignored and gets silently overwritten by whatever `hardhat.config.ts` says at the last local `compile`, with no history. Git history showed CeloBankAgent was added at `fb64178` (May 15 2026) when `hardhat.config.ts` set `solidity: "0.8.25"`; that line wasn't touched again until `eaa0abc` (June 10 2026), the same commit that added TokenFactory and bumped it to `0.8.28`. The first `standard-json-input.json` (generated from a compile run after that bump) used 0.8.28 for both contracts — correct for TokenFactory, wrong for CeloBankAgent. Fetched the real on-chain deployed bytecode for both contracts from `celo.blockscout.com` (keyless; Celoscan's own API rejected this project's key on the v2 endpoint) and locally recompiled with a standalone `solc` package outside Hardhat entirely: CeloBankAgent under solc 0.8.25/no-optimizer matched the live bytecode at 8 spot-checks spread across its full 13,381 bytes (only the non-functional metadata-hash tail differs, which Etherscan-family verifiers tolerate); TokenFactory under 0.8.28/no-optimizer matched the first ~2,900 bytes of its own dispatcher logic exactly, confirming its original file was already correct. New corrected file: `celoscan-verify/celobankagent-standard-json-input.json` (compiler `v0.8.25+commit.b61c2a91`). TokenFactory's file renamed for clarity to `celoscan-verify/tokenfactory-standard-json-input.json`, unchanged.
- July 23 2026 (later still): **Zod override conclusively disproven; manual Celoscan verification files generated instead.** Retried the npm `overrides` fix from the entry below with an exact-pinned `zod` version instead of a caret range — still didn't take. Proved *why* with an isolated 2-dependency repro (just `hardhat` + `zod`, no other packages): `@nomicfoundation/hardhat-zod-utils` declares `zod` only as a `peerDependency`, never as a real `dependencies` entry, so there is nothing for npm's `overrides` to override — this is a structural npm limitation, not a version-pinning mistake. Removed the dead `overrides` block from `package.json` entirely (it did nothing). Instead extracted the exact Standard-JSON-Input Hardhat used for the last successful compile (`artifacts/build-info/solc-0_8_28-...json`, confirmed via matching `buildInfoId` to be the literal input that produced both deployed contracts' bytecode) and handed it off for manual verification via Celoscan's web UI — see `standard-json-input.json` / `VERIFY_INSTRUCTIONS.md`.
- July 23 2026 (later same day): **`npx hardhat verify` attempt reverted — breaks `npx hardhat compile` too.** Registering `@nomicfoundation/hardhat-toolbox-viem` as a real Hardhat 3 plugin (required for `npx hardhat verify` to exist at all) pulls in `@nomicfoundation/hardhat-verify`, which bundles its own Zod v3. This project's own code depends on Zod v4 (`"zod": "^4.4.3"`). When Hardhat merges every registered plugin's config schema for validation, schema fragments built by different physical Zod module instances get cross-parsed, crashing with `TypeError: keyValidator._parse is not a function` — confirmed as a known Zod dual-instance/plugin-boundary compatibility issue (not fixable via version pinning or npm `overrides`; both were tried). Worse, this crash fires during Hardhat's generic config-validation hook, so it broke *every* Hardhat command, not just `verify` — `npx hardhat compile` failed identically. Reverted `hardhat.config.ts` and `package.json`/`package-lock.json` back to not registering the plugin, restoring normal `compile`. Contract verification (CeloBankAgent identity registry: `0x4ebef67f7a20485ccc9e66ee58fcc99f23e93de1`; TokenFactory: `0x597f121c014b99a15c7c4e08928f0fe1ec3adc2e`, both on Celo Mainnet) should instead be done manually via Celoscan's "Verify and Publish Contract Source Code" web UI, using the Standard-JSON-Input generated by a plain `npx hardhat compile` (found under `artifacts/build-info/`) — this sidesteps the Hardhat/Zod toolchain entirely. Don't re-attempt the CLI `hardhat-verify` route without first checking whether upstream has fixed the Zod v3/v4 plugin-merging issue.
- July 23 2026: **Divvi referral-tag integration evaluated and removed.** A same-week addition tagging every prepared transaction's calldata with a Divvi referral tag (to cover third-party protocol calls Karma GAP's ownership-based tracking can't see) was pulled back out after confirming the service is discontinued — `@divvi/referral-sdk` is deprecated on npm, the `divvi-xyz` GitHub org is archived, and `app.divvi.xyz` no longer resolves. Don't re-add this blindly later without re-checking Divvi's status first. The existing Celo Builders (ERC-8021) attribution tag is unaffected and remains in place across every entry point.
- July 18 2026 (later same day): **Live bug found during Proof-of-Ship testing — nonce race in multi-step transaction flows.** After deploying the fixes below, a real `swap_tokens` (CELO→cUSD via Mento V2) failed on mainnet with `"nonce too low: next nonce 22, tx nonce 21"`. Root cause: `executePrepared()` in `src/ui/App.tsx` — the generic executor used for every multi-transaction flow (swap's approve+swap, unstake's 3-step withdraw) — let the wallet client auto-derive each transaction's nonce instead of fetching it explicitly. This is the same class of bug already fixed for `doCheckIn`/`doClaimReward` (July 14, ref-based lock + explicit nonce), but that fix was never extended to `executePrepared`, so any prepared flow with 2+ sequential transactions could still hit a stale nonce — some wallets (MiniPay included) appear to track nonces optimistically client-side rather than re-querying pending state right after a `waitForTransactionReceipt`. Fixed by fetching a fresh `getTransactionCount({ blockTag: "pending" })` immediately before every send in the loop (not just once at the start), plus a friendlier "Transaction conflict (nonce) — please try again" message instead of the raw RPC error. Confirmed working end-to-end separately: the `launch_token` fix from the same day was verified live on Celo Mainnet (tx `0xf9efd2a2f855eef84bc4592c4b9fba6d4ac35354a013fd0c6059260f360d40ed`, CBTEST token deployed via TokenFactory, 1,000 tokens minted).

- July 18 2026: **Third audit pass — functional-correctness bugs + security hardening.** Found and fixed: (1) `get_portfolio` and `get_balance` had their implementations swapped — `agent.ts` imported `get_balance` from `celo.ts` (which actually returned the full multi-token portfolio) and `get_portfolio` from `defi.ts` (which only ever returned the native CELO balance, contradicting its own description and the `/api/v1/portfolio/:address` REST endpoint's documented JSON shape). Fixed by giving `celo.ts` a genuine lightweight `get_balance` (CELO only) and making `defi.ts` re-export `celo.ts`'s full portfolio/multi-price implementations instead of maintaining incomplete duplicates. (2) `get_engagement_rewards` defaulted to the zero address when called without an explicit address (the README's own example usage) because it read `process.env.AGENT_ADDRESS`/`CELOBANK_APP_ADDRESS`, neither of which exists in `.env` — always returning zeroed-out stats instead of CeloBank's real onboarding numbers. Fixed to derive the real agent address from `PRIVATE_KEY`, same as every other tool module. (3) **`send_celo`/`prepareSend` only ever supported native CELO**, even though the app's own GoodBuilders application advertises `"envoie 5 cUSD à mon ami"` as a working example — a request to send a stablecoin had no matching tool and risked the model substituting a CELO transfer for a stablecoin one (wrong asset, wrong value). Added generic ERC20 support: `prepareSend(userAddress, to, amount, token = "CELO")` now sends any registered token via `transfer()`, wired through `tools/celo.ts`, `agent/agent.ts`'s tool schema, `server.ts`'s REST/MCP surfaces, the SDK's `send()`, and the UI's local intent regex (previously hardcoded to match only the literal word "celo"). (4) `get_trending_tokens` was implemented, registered in the AI tool registry, and listed in `/catalog` and `TOOL_SCHEMAS` — but missing from the `MCP_TOOLS` array that `POST /mcp`'s `tools/list` and `tools/call` guard actually check, so any external MCP client calling it got `"Unknown tool"` even though the underlying function worked. Added it to `MCP_TOOLS`. (5) Tool counts were wrong everywhere (`/health`, `/mcp` discovery payload, agent-card, README, WHITEPAPER, GOODBUILDERS application) — actual count is 24 (15 free + 9 paid), not the previously-stated 21 (14 free + 7 paid); the "7 paid tools" list also named four tools that don't exist in the codebase (`supply_aave`, `borrow_aave`, `repay_aave`, `check_in`) instead of the real ones. Corrected everywhere. (6) The Farcaster webhook (`src/bot/farcaster-bot.ts`) **failed open**: if `NEYNAR_WEBHOOK_SECRET` was ever unset, `verifyNeynarSignature()` returned `true` (accepting every unsigned request as legitimate) instead of rejecting; separately, `crypto.timingSafeEqual()` throws (not returns `false`) on a length mismatch, so a malformed signature header could crash the request. Fixed to fail closed with a startup warning, and to check buffer lengths before comparing. (7) `src/lib/self-agent-id.ts` imports `ethers`, which was never declared in `package.json` — it only resolved via transitive hoisting from another dependency, a fragile "phantom dependency" that could break on a strict install. Added explicitly. (8) The Self Agent ID owner-registration signature (`POST /api/self-agent-register`) signed a static message with no nonce or expiry, making a captured signature replayable indefinitely. Added a timestamp to the signed message and a 5-minute server-side validity window. (9) The README's Security table claimed active Supabase RLS enforcement (`agent_actions`/`agent_stats`) as a live control; in reality no code path in `src/` ever calls Supabase — the migration exists but is not wired in. Corrected the README to state this honestly. SDK (`@celobank/agent-sdk`) bumped to **1.2.0** in source for the `send()` token-support fix — **not yet published**; `npm publish` still requires the maintainer's own npm credentials (same caveat as the prior 1.1.1 bump).

- July 14 2026: **Critical fix — complete 3-phase unstake flow.** `prepareUnstake()` (the existing `unstake_celo` tool) only ever implemented step 1 of StakedCelo's required 3-step withdrawal (`Manager.withdraw`, which schedules the unstake but does not unvote CELO from validator groups or start the unlock countdown). Without steps 2 and 3, a user's CELO could be scheduled for unstake and then sit frozen indefinitely — the Manager contract has no automatic mechanism to finish the process. Added two new fully non-custodial tools/endpoints: `continue_unstake` (step 2 — calls `Account.withdraw` per validator group, computing exact sorted-list neighbor hints against `Election.getTotalVotesForEligibleValidatorGroups()` to unvote and start the 3-day `LockedGold` unlock countdown) and `claim_unstake` (step 3 — matches pending withdrawals by value+timestamp against `Account`/`LockedGold` and calls `Account.finishPendingWithdrawal` once each entry's unlock time has passed). Both return unsigned transactions only, signed by the connected user's own wallet — no agent keeper or backend signer was introduced. Wired end-to-end: `tools/prepare.ts` (core logic, verified against live contract source and current post-L2-migration Celo Mainnet addresses), `tools/staking.ts` + `agent/agent.ts` (LangChain/Anthropic tool definitions, with the AI system prompt updated to explain the 3-step process and never imply step 1 alone releases funds), `server.ts` (REST `/api/v1/prepare`, MCP `POST /mcp`, `/catalog`, `WRITE_TOOL_NAMES` for x402 enforcement), and `ui/App.tsx` (local intent regex for "continue unstake"/"claim unstake" phrasing, checked before the generic unstake pattern to avoid the same substring bug fixed earlier for "unstake"/"stake"; a follow-up hint is now shown after each step confirms, prompting the user toward the next one). **Caveat**: this is genuinely new on-chain protocol logic (sorted-linked-list neighbor computation, pending-withdrawal index matching) that could not be fork-tested end-to-end in this environment — recommend testing with a small amount first before relying on it for larger unstakes.
- July 14 2026: **Second audit pass** — full sweep of every module not covered by the first pass (DailyDrop, GoodDollar, Self Protocol registration, Farcaster bot, all server endpoints). Found and fixed: (1) `doCheckIn()`/`doClaimReward()` in the UI had a double-click nonce race — React state disables the button only after a render, so a fast double-click could fire two wallet transactions before either landed, causing "nonce too low" on-chain errors; fixed with a synchronous ref-based lock plus explicit fresh-nonce fetching. (2) The frontend's local intent regex matched "unstake 5" as a **stake** action (the word "stake" is a substring of "unstake"), which would have prepared the exact opposite transaction the user asked for; fixed by checking the unstake pattern first. (3) `POST /api/v1/prepare` (the documented public REST endpoint) never had an `unstake` case — only the MCP endpoint did — so any external API/SDK caller requesting `action: "unstake"` got "Unknown action"; added the missing case, validation, and OpenAPI enum entry. (4) The Farcaster bot (`src/bot/farcaster-bot.ts`) called `runAgent()` directly and had no handling for the unsigned-transaction marker used by all six write tools — if a Farcaster user triggered a write action, the bot would have publicly cast the raw internal `__CELOBANK_UNSIGNED_TX__{...}` JSON payload as a reply; fixed to detect the marker and reply with a summary + link to the web app instead. (5) SDK README's x402 changelog note listed three MCP tool names that don't exist in the codebase (`supply_aave`, `borrow_aave`, `repay_aave`, `check_in`) instead of the real ones (`save_cusd`, `swap_celo`, `stake_celo`, `unstake_celo`); corrected to match the actual `WRITE_TOOL_NAMES` set. (6) `/api/self-agent-status` and `/api/self-agent-register` had no rate limiting, inconsistent with every other public endpoint; added.

- July 14 2026: **Critical fix** — write tools reachable via the AI chat path (`send_celo`, `swap_celo`, `swap_tokens`, `save_cusd`, `stake_celo`, `unstake_celo`) were signing and broadcasting transactions with the agent's own private key instead of returning unsigned transactions for the user to sign, contradicting the non-custodial v2 architecture.
